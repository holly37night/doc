概要やりたいこと4点

現行の東横イン支配人AIは、ローカルの doc/ フォルダをスクリプト（ingest_docs.py）で手動プッシュしてRAG登録し、Qdrant／DynamoDB Local／Postgres を docker-compose で動かしています。今回の改修は次の4点です。

1現状構成（ローカル docker-compose）

全サービスが1台のPC上のコンテナで完結。ファイル取込は人手でスクリプトを実行する“プッシュ型”。RAGデータ（ベクトル・画像・メタデータ）はローカルボリューム上にあり Git 管理外。

現状の課題
  • 取込が手動プッシュ（ingest_docs.py をPCで実行）。担当者・端末に依存する。
  • 原本は manual-assets/<manual_id>/ のローカル保存。共有・可搬性・バックアップが弱い。
  • updated_at は「取込した時刻」で、ファイル本来の更新日ではない。
  • 参照元リンクはバックエンドのローカルファイル配信に依存（S3の恒久URLがない）。
  • 画像の向き補正が Gemini Vision の判定のみで、EXIF回転や誤判定に弱い。

2目標構成（S3イベント取込 ＋ RAG on ECS）

S3を「原本の置き場」兼「取込トリガ」にし、RAG（API・取込ワーカー・Qdrant・メタデータ）をAWSへ移設します。要望2の「現状のRAGだけ」に合わせ、まずは点線枠のRAGコアだけをECS化し、フロント/管理画面は段階移行とします。

設計上のポイント

  • S3イベント → SQS → 取込ワーカーで疎結合化。大きいファイルや同時多発でもキューで平準化。
  • QdrantはFargate＋EFSで永続化。既存のエクスポート/インポート手順（export-rag-data.ps1）で初回データ移行が可能。
  • 取込ワーカーは既存の manual_ingestion.import_manual() をほぼ再利用し、入力元をローカル→S3に差し替える。
  • APIとワーカーを別サービスに分離し、取込の重い処理が回答応答を圧迫しないようにする。

3シーケンス：S3配置 → 自動RAG登録

ファイルをS3に置くと、以降は無人で取込が完走します。冪等性（同一キーの再取込は上書き）と、S3の LastModified／ファイル内部の更新日を取り込む点がポイントです。

4シーケンス：質問応答 → S3リンクで原本を開く

51マニュアルあたりの登録データ構造（追加項目）

既存の ManualDocumentResponse / SourceManual に、S3パスとファイル更新日を追加します。現状 updated_at は取込時刻のため、ファイル由来の更新日は別項目として明確に持ちます。

ManualDocumentResponse（マニュアル本体メタデータ）

項目型区分説明 / 取得元
manual_idstr既存マニュアルID
titlestr既存ファイル名（拡張子除く）
file_typeenum既存pdf / docx / xlsx / pptx
source_pathstr変更ローカルパス →（当面は互換保持しつつ）S3参照へ移行
s3_uristr追加S3のパス。例 s3://manuals-bucket/manuals/xxx.pdf。UIのリンク元
s3_bucket / s3_keystr追加presigned URL発行に使う分解値
file_updated_atdatetime追加ファイルの更新日。文書内部の更新日時（docxコアプロパティ / PDF ModDate）を優先し、無ければ S3 LastModified
updated_atdatetime既存RAGへ取込・再索引した時刻（意味を「取込時刻」に明確化）
chunks[] / pictures[]list既存本文チャンク / 抽出画像

ManualPicture（抽出画像）

項目区分説明
asset_path変更ローカルパス → S3キー参照へ
s3_key追加画像バケット上のキー。表示用presigned URLを発行
rotation_applied追加補正で適用した回転角(0/90/180/270)。監査・再処理用
caption / description既存Vision生成の日本語説明（検索対象）

SourceManual（回答時にUIへ返す参照元）

項目区分説明
title / manual_id既存参照元名
download_url変更ローカル配信 → S3 presigned URL（クリックで原本を開く）
file_updated_at追加更新日バッジ表示用
「ファイルから取得」の実装方針：
  • DOCX/XLSX/PPTX：OOXMLの docProps/core.xml の dcterms:modified を読む（python-docx / openpyxl / zipで取得可）。
  • PDF：メタデータ /ModDate（pypdf reader.metadata.modification_date）。
  • 文書内に更新日が無い場合のみ、S3オブジェクトの LastModified をフォールバックに使う。

6画像の向き補正の改善

現状は _describe_image_with_orientation() が Gemini Vision の回転判定のみに依存し、①スマホ/タブレット撮影画像の EXIF Orientation 未対応、②Vision誤判定時の救済なし、という弱点があります。EXIF → アスペクト比ヒューリスティック → Vision の多層判定に改善します。

改善の要点

  • EXIF優先：撮影画像はまず exif_transpose() で確実に正立化。Visionを呼ぶ前に大半が解決。
  • アスペクト比ゲート：明らかな縦長/横長のみVisionで再確認し、API呼び出しと誤回転を削減。
  • 正規化保存：補正後にEXIFを剥がして保存し、ブラウザ/OSの再回転による“二重回転”を防止。
  • 監査性：rotation_applied を保持し、誤りは再取込（reindex）で修正可能に。

変更対象

  • services/manual_ingestion.py の _extract_page_images() / _describe_image_with_orientation()
  • DOCX/PPTX/XLSXの画像抽出経路にも同じ補正を適用（現状はPDF中心）。
  • 依存は既存の Pillow 11.2.1 で対応可（追加ライブラリ不要）。

図6-2. 補正の中核ロジック（実装イメージ）

from PIL import Image, ImageOps

def normalize_orientation(blob: bytes, ext: str) -> tuple[bytes, int]:
    img = Image.open(io.BytesIO(blob))
    # ① EXIF Orientation を尊重して正立化（撮影画像に有効・ロスレス）
    img = ImageOps.exif_transpose(img)
    applied = 0

    # ② アスペクト比ゲート：横倒しが疑われる場合のみ Vision 確認
    w, h = img.size
    suspect = (w / h) > 1.6 or (h / w) > 1.6
    if suspect:
        rotation = ask_gemini_rotation(img)   # 0/90/180/270
        if rotation in (90, 180, 270):
            img = img.rotate(-rotation, expand=True)
            applied = rotation

    # ③ EXIF を除去して正規化保存（二重回転を防止）
    buf = io.BytesIO()
    fmt = "JPEG" if ext == "jpg" else ext.upper()
    img.save(buf, format=fmt, **({"quality": 95} if fmt=="JPEG" else {}))
    return buf.getvalue(), applied
