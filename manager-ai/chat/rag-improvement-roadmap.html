現行の検索パイプライン実測に基づく、効果×工数で優先度づけした改善計画 — 作成日 2026-08-12

0現状評価 ＆ 核心

現行 rag_service.retrieve() はすでに高度です。以下が実装済みで、精度側は素朴な密ベクトル検索から大きく進化しています。

  • クエリからの LLMタグ生成、マルチクエリ拡張、HyDE（仮説回答をドキュメント埋め込みで検索）
  • 密ベクトル検索（タグ絞り込み＋通常＋拡張＋HyDE）＋ キーワード検索の併用（簡易ハイブリッド）
  • LLMリランキング＋フィードバック学習リランク（実績係数のブレンド）
  • 埋め込みは RETRIEVAL_QUERY／RETRIEVAL_DOCUMENT を正しく使い分け（768次元・Gemini）
核心の診断：現状は「精度リッチだが往復が多く遅い」。1クエリあたり Gemini へ 逐次で4〜5回（タグ生成→拡張→HyDE→埋め込み→LLMリランク）＋ Qdrant へ複数回検索している。したがって最大の伸びしろは 速度、精度は 語彙一致（型番・エラーコード）と評価による最適化に集約される。

6優先度つきロードマップ

Phase 1: クイックウィン低リスク・即効

前段3コールの並列化/統合、Qdrant gRPC化、ペイロードインデックス、クエリ/回答キャッシュ。精度はそのままレイテンシを大幅短縮。既存の検索品質を落とさず体感を最優先で改善。

Phase 2: スパースハイブリッド化精度＋速度

Python完全一致検索を Qdrantスパースベクトルへ置換し、Query API の prefetch＋RRF融合で1リクエストに集約。型番・エラーコードの取りこぼしを構造的に解消しつつ往復も削減。

Phase 3: 評価ハーネス改善の土台

verified_qa から recall@k / MRR / レイテンシを自動計測。以降の変更はすべてこの数値で採否判断。

Phase 4: チャンク改良・OCR・次元調整精度の作り込み

親子チャンク/手順単位分割、画像OCRテキスト付与、埋め込み次元の見直し。Phase 3の指標で効果を確認しながら反映。

おすすめの入り口：Phase 1（クイックウィン）は既存ロジックを壊さずレイテンシだけ落とせるので最初に。次にPhase 2で語彙一致の精度を底上げ、Phase 3で計測基盤を作ってからPhase 4を数値ドリブンで進める。
