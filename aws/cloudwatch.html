CloudWatch の仕組み

「監視サービス」と一括りにされがちですが、実際は中身の違う複数の仕組みが 同じ名前の下に同居しています。どこに何が記録され、どう取り出すのかを整理した記録です。

2026 / 全 7 章

まず覚える一行

名前空間＋ メトリクス名＋ ディメンション＝ 時系列 1 本

この 3 つの組み合わせが、グラフに描かれる線 1 本を決めます。 ディメンションが 1 つ違えば別の線になる、という性質がすべての土台です。

01

2系統に分かれている

CloudWatch に入ってくるデータは、大きくメトリクス（数値）と ログ（テキスト）の 2 系統です。保存場所も、取り出し方も、料金体系も別物です。 ここを混同しないことが理解の第一歩になります。

02

メトリクス

数値の時系列データです。AWS のサービスが自動で送ってくるので、こちら側で設定するものはありません。

ディメンションの組み合わせ

同じ 5XXError でも、API Gateway は複数の粒度で送ってきます。 粒度ごとに別のメトリクスとして存在するのがポイントです。 

{ApiName}                          ← API全体の合計
{ApiName, Stage}                   ← ステージ別
{ApiName, Stage, Resource, Method} ← メソッド別（詳細メトリクス有効時のみ）

ダッシュボードを「API 別に分けたい」と思ったとき、追加の設定が要らないのはこの構造のおかげです。 取り出すときにディメンションを指定するだけで分かれます。

統計と期間は「見るとき」に決める

ここが直感に反するところです。CloudWatch は生のデータポイントを保持していて、 Sum なのか Average なのか p95 なのかは、グラフを描く瞬間に指定します。 記録時に悩む必要はなく、あとから別の見方に変えられます。

統計意味よく使う場面
Sum期間内の合計リクエスト数、エラー数
Average期間内の平均CPU 使用率などの傾向
Maximum期間内の最大値ピーク検出。スロットリングの値決め
Minimum期間内の最小値空き容量の下限確認
SampleCountデータポイント数データが来ているかの確認
p95 / p99パーセンタイルレイテンシ
レイテンシに Average は使わない

平均値は、少数の極端に遅いリクエストを希釈してしまいます。 1,000 件のうち 50 件が 10 秒かかっていても、平均では見えません。 レイテンシは p95 か p99 で見るのが定石です。

保持期間とロールアップ

古いデータは自動的に集約され、解像度が粗くなっていきます。

解像度保持期間
1 秒未満（高解像度）3 時間
1 分15 日
5 分63 日
1 時間15 か月

つまり半年前のデータを 1 分刻みで見ることはできません。 長期の詳細な記録が必要なら、S3 へエクスポートするか、メトリクスストリームで別基盤へ流す設計が要ります。 逆に言えば、直近の障害調査であれば 1 分解像度が使えるので、期間を絞って見るのが有効です。

03

ログ

テキストの記録です。3 階層になっています。

階層何を表すかここに紐づく設定
ロググループログの入れ物保持期間、暗号化、IAM 権限、サブスクリプション
ログストリーム送信元 1 つ分（設定なし）
ログイベント1 行のログ（設定なし）

設定がすべてロググループ単位である点が実務上の要点です。 「保持期間を分けたい」「権限を分けたい」なら、ロググループを分けるしかありません。 同じロググループに複数のシステムのログを混ぜると、あとから分離できなくなります。

保持期間の既定は無期限

ロググループを作った直後は保持期間が「失効しない」になっています。 放置すると保存料金が増え続けるので、作成時に必ず設定してください。 本番のアクセスログなら 90 日〜1 年、開発環境なら 14〜30 日あたりが目安です。

ログを数値に変える 2 つの仕組み

仕組み何をするか使いどころ
メトリクスフィルターログ中の文字列にマッチした回数をメトリクス化「ERROR という文字が出た回数」でアラームを張る
サブスクリプションフィルターログをリアルタイムで他へ転送Lambda で加工、OpenSearch へ、S3 へ

アラームはメトリクスにしか張れません。 ログの内容をトリガーに通知したい場合は、メトリクスフィルターでいったん数値に変換する必要があります。 これが図の左右をつなぐ橋にあたります。

Logs Insights

ロググループに対してクエリを打てます。ログを JSON 形式で出しておくと、 フィールド名でそのまま絞り込めるので、アクセスログの設計時点で JSON にしておく価値があります。 

fields @timestamp, resource_path, status, responseLatency
| filter status >= 500
| stats count() by resource_path
| sort count desc

ドメインやステージが同じロググループに混在している場合も、 | filter domain = "ota-api.example.com" のように絞り込めます。 ただし保持期間やアラームは分けられないので、あくまで応急処置です。

課金はスキャン量に対して

クエリが読んだデータ量で課金されます。期間を絞ってから実行するのがコツで、 いきなり「過去 1 か月」で流すと想定外の請求になることがあります。

04

アラーム

メトリクスに閾値を設定し、3 つの状態を持ちます。

状態意味
OK閾値内
ALARM閾値を超えた
INSUFFICIENT_DATAデータが足りない
欠落データの扱いが最大の落とし穴

「エラー数が 5 件を超えたら通知」というアラームは、 エラーがゼロの時間帯はデータポイント自体が存在しません。 その結果 INSUFFICIENT_DATA になり、正常なのに警告扱いされます。 アラーム作成時の「欠落データの処理」を「良好（notBreaching）」に 設定しておくのが定番の対処です。

評価条件

「N 回中 M 回が閾値超えなら発報」という形で指定できます。 1 回のスパイクで叩き起こされないよう、3回中2回 のような設定にするのが実用的です。 逆に即応が必要なものは 1回中1回 にします。

アラームの種類

種類内容使いどころ
静的閾値固定値と比較基本形。5XX が 10 件以上、など
異常検出過去の傾向から機械的に範囲を学習時間帯で変動が大きいリクエスト数
メトリクス数式複数メトリクスを計算した結果に対してエラー率（5XX ÷ Count）で判定
複合アラーム複数アラームの AND / OR「エラー増加 かつ レイテンシ悪化」で発報

件数ではなく率で見たい場合はメトリクス数式が有効です。 アクセスが増えればエラー件数も自然に増えるため、固定件数の閾値は誤報の元になります。

05

料金の勘所

無料で取れるものと課金されるものの区別が、設計判断に直結します。

項目課金備考
AWS サービスの標準メトリクス無料API 単位・ステージ単位はここ
詳細メトリクス（メソッド別など）課金カスタムメトリクス扱い。本数で効いてくる
カスタムメトリクス課金1 本ごとに月額
ログの取り込み量課金費用の大半はここ
ログの保存量課金保持期間に比例
Logs Insights のクエリ課金スキャンしたデータ量に応じて
ダッシュボード3 つまで無料4 つ目から月額
アラーム10 個まで無料高解像度アラームは別料金
典型的な浪費パターン

① 実行ログを INFO にしたまま本番運用（全リクエストの処理過程が記録される）
② データトレースを有効にしたまま戻し忘れ（リクエストボディが丸ごと記録される）
③ ロググループの保持期間が無期限のまま
④ 使っていない API で詳細メトリクスが有効
いずれも設定を戻すだけで下がるので、まず現状を棚卸しする価値があります。

カスタムメトリクスは高カーディナリティに注意してください。 ディメンションに会員 ID やリクエスト ID のような値を入れると、値の種類の数だけメトリクスが生成され、 料金が一気に膨らみます。ディメンションに入れてよいのは「種類が有限で、集計軸として意味のあるもの」だけです。

06

名前空間とメトリクス名

API Gateway

名前空間 AWS/ApiGateway
メトリクス名意味推奨の統計
Countリクエスト数Sum
4XXErrorクライアント起因のエラーSum
5XXErrorサーバー起因のエラーSum
Latency受信から応答返却までの合計時間p95 / p99
IntegrationLatencyバックエンドの処理時間p95
CacheHitCountキャッシュから返した数Sum
CacheMissCountキャッシュを外した数Sum
DataProcessed転送バイト数（HTTP API のみ）Sum

Latency と IntegrationLatency の差が API Gateway 自身のオーバーヘッドです。この 2 本を並べれば、 遅いのがバックエンドなのかゲートウェイなのかが即座に判別できます。

キャッシュを有効にしている API では CacheHitCount を必ず確認してください。 両方ゼロなら、クラスタ料金だけ払って全く効いていない状態です。 ステージでクラスタを起動しても、メソッド側で有効化しないとキャッシュされません。

ディメンションの粒度
ディメンション粒度課金使いどころ
{ApiName}API 全体無料ドメイン別ダッシュボード
{ApiName, Stage}ステージ別無料環境別・機能グループ別
{ApiName, Stage, Resource, Method}エンドポイント別課金遅いエンドポイントの特定
{ApiId, Stage}HTTP API 用無料REST API では使われない
ドメイン名のディメンションは存在しない

CloudWatch にドメイン単位の軸はありません。ドメイン別に分けられるのは、 1 ドメイン = 1 API になっている場合だけです。 1 つの API に複数ドメインを向けると、メトリクスでは永久に分離できなくなります。 「1 ドメインにつき 1 API」を規約にしておくと、この分析可能性が守られます。

名前空間代表的なメトリクス主なディメンション

AWS/RDSCPUUtilization, DatabaseConnections, FreeableMemory, ReadLatencyDBInstanceIdentifier

AWS/Lambda の Throttles と ConcurrentExecutions は、 API Gateway のメトリクスと並べて見ると効きます。 API Gateway で受け止めきれても Lambda 側で詰まることがあるためです。

AWS/WAFV2 の BlockedRequests は、WAF 導入直後の誤検知監視に使います。 正常なリクエストがブロックされていないかを、カウントモードの段階で確認できます。

カスタム名前空間

アプリから自前のメトリクスを送ることもできます。AWS/ で始まらない任意の名前が使えます。 

MyCompany/Booking  →  ReservationCompleted, PaymentFailed

送る手段は PutMetricData API か、ログに埋め込む EMF（Embedded Metric Format）です。 EMF は「ログを出すついでにメトリクスも生成される」仕組みで、アプリ側の実装が軽くなります。

利点は、ビジネス指標を技術指標と同じダッシュボードに並べられることです。 「エラーは出ていないのに予約が止まっている」といった、技術メトリクスだけでは気づけない異常を検知できます。

07

実例と探し方

探し方

コンソールでは、CloudWatch → メトリクス → すべてのメトリクス。 名前空間 → ディメンションの組み合わせ → メトリクス、の順に絞り込むツリーになっています。

CLI なら、実際に存在するものだけが返るので確実です。

aws cloudwatch list-metrics \
  --namespace AWS/ApiGateway \
  --dimensions Name=ApiName,Value=<API名> \
  --region ap-northeast-1

ドキュメントを読むより、この出力を見るほうが早く正確です。

実例：本数の差が示すもの

同じ API Gateway でも、設定によってメトリクスの本数が大きく変わります。

シンプルな API詳細メトリクス有効の API
メトリクス本数10 本前後数百本
ディメンション{ApiName} と {ApiName, Stage} のみ上記＋ {ApiName, Stage, Resource, Method}
料金無料エンドポイント数 × メソッド × 指標数で課金
分かることAPI 全体・ステージ単位の傾向どのエンドポイントが遅いか、まで特定できる

本数が膨らむ原因はもう 1 つあります。使っていないステージです。 ドメインにマッピングされていない検証用ステージが残っていると、その分もメトリクスとして出続けます。 棚卸しの際は、ステージ一覧とドメインのマッピングを突き合わせてみてください。

メトリクス数式の読み方

ダッシュボードのウィジェットは、メトリクスを直接指定するほかに数式で書けます。 既存のダッシュボードを引き継いだときは、まずこれを読み解くところから始まります。 実際によく見かける形がこちらです。 

SUM(SEARCH('{AWS/ApiGateway,ApiName} ("5XXError")', 'Sum', 3600))
分解すると
部分何をしているか
SEARCH(...)条件に合うメトリクスをすべて探し、それぞれ 1 本の線として返す
{AWS/ApiGateway,ApiName}名前空間が API Gateway で、ディメンションが ApiName だけのもの
("5XXError")メトリクス名に 5XXError を含むもの
'Sum', 3600各線を 1 時間ごとの合計で描く
SUM(...)返ってきた複数の線を、1 本に足し合わせる
「分析しにくい」の正体

グラフが 1 本しか出ず、どの API が原因か分からない——という症状のほとんどは、 この外側の SUM() が原因です。 直し方は単純で、SUM() を外すだけ。それだけで API ごとに線が分かれ、 凡例に名前が出ます。

SEARCH は自動で追従する

SEARCH は実行のたびに条件に合うものを探し直します。つまり 新しい API を作れば自動的に線が増え、削除すれば自動的に消えます。 ウィジェットのメンテナンスが不要という意味で、本来は優れた仕組みです。 問題は集約の仕方だけで、探す部分は触る必要がありません。

ディメンションは完全一致で照合される

{AWS/ApiGateway,ApiName} は、ディメンションが ApiName だけの メトリクスにしか一致しません。{ApiName, Stage} のステージ別メトリクスは含まれないため、 二重計上は起きません。

裏を返せば、ステージ別の内訳はこの式では見えません。必要なら指定を変えます。

SEARCH('{AWS/ApiGateway,ApiName,Stage} MetricName="5XXError"', 'Sum', 3600)

なお ("5XXError") は「メトリクス名に含まれる」という緩い検索です。 MetricName="5XXError" と書けば完全一致になり、意図が明確になります。

内訳と合計を両方見たい場合

"metrics": [
  [ { "expression": "SEARCH('{AWS/ApiGateway,ApiName} MetricName=\"5XXError\"', 'Sum', 3600)", "id": "e1" } ],
  [ { "expression": "SUM(e1)", "label": "全API合計", "id": "e2" } ]
]

内訳の線と合計の線が同時に描かれます。ただし線が増えて見づらくなるので、 合計は別ウィジェットに分けるほうが実用的です。

よく使う数式関数

関数何をするか使いどころ
SEARCH条件に合うメトリクスを複数返すAPI 別・インスタンス別に自動で線を分ける
SUM複数の線を足して 1 本に全体の総数を出す（内訳は消える）
AVG複数の線を平均して 1 本にクラスタ全体の平均 CPU など
METRICS()そのウィジェットの全メトリクスSUM(METRICS()) で合計行を足す
FILL欠落データを埋めるゼロ件の時間帯を 0 として描く
RATE秒あたりの変化量に変換累積値を流量として見る
a/b*100四則演算エラー率（5XX ÷ Count）で判定する
ANOMALY_DETECTION_BAND正常範囲の帯を描く時間帯変動が大きい指標の異常検知

件数ではなく率で見たいときは四則演算が効きます。 アクセスが増えればエラー件数も自然に増えるため、固定件数の閾値は誤報の元になるからです。

ダッシュボードで API 別に分ける

検索式を使うと、API 名ごとに自動で線が分かれます。 新しい API を作っても勝手に追加されるので、メンテナンスが不要になります。 

SEARCH('{AWS/ApiGateway,ApiName} MetricName="5XXError"', 'Sum', 3600)

ステージまで分けたい場合はこちらです。

SEARCH('{AWS/ApiGateway,ApiName,Stage} MetricName="5XXError"', 'Sum', 3600)

個別に指定して label を付ける方法もあります。 凡例に API 名ではなくドメイン名を出せるので、 API 名を知らない人でも読めるダッシュボードになります。 

"metrics": [
  [ "AWS/ApiGateway", "5XXError", "ApiName", "<API名>", { "label": "ota-api" } ]
],
"stat": "Sum",
"period": 3600

ダッシュボードの組み立て方

指標を重ねるより、同じ並び順で縦に積むほうが読み解けます。

  1. リクエスト数

    Count を Sum で。まず全体の流量を把握する。

  2. 5XX エラー

    サーバー起因。上の段と時間軸が揃っているので、流量増加が原因かどうか目で追える。

  3. 4XX エラー

    クライアント起因。認証切れや仕様変更の検知に。

  4. レイテンシ

    Latency を p95 で。IntegrationLatency も重ねると切り分けが早い。

2 軸グラフの副作用

桁の違う指標を左右の軸で重ねると、片方が異常値でも目盛りに埋もれて気づきにくくなります。 指標ごとにウィジェットを分けるほうが実用的です。

便利なウィジェット

やりたいこと設定
異常値の基準線を引くウィジェットのオプション →「水平方向の注釈」
アラーム状態を色で出す「アラーム」ウィジェットを追加
ログの検索結果を貼るLogs Insights でクエリ実行 →「ダッシュボードに追加」
説明文を入れる「テキスト」ウィジェット（Markdown 可）

テキストウィジェットは地味に有効です。冒頭に「このグラフの見方」「異常時の連絡先」を書いておくと、 当番が代わっても迷いません。
