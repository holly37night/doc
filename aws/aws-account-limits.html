アカウントで
共有されるもの

設定を分けたいとき、どこまでがアカウント内で分離でき、どこからがアカウントを 分けないと不可能なのか。その境目を整理した記録です。 アカウント分割は最後の手段であり、たいていの要件はその手前で満たせます。

2026 / 全 7 章

TYPE 1 共有される枠 誰かが使い切ると、他が使えなくなる。影響が最も大きい
TYPE 2 1つしか持てない設定 分けたくても分けられない。請求やパスワードポリシーなど
TYPE 3 名前空間の衝突 命名規約で回避できる。分割の理由にはならない
TYPE 4 巻き添えリスク 枠ではないが影響が及ぶ。誤操作の射程がここに含まれる
01

共有される「枠」

アカウント＋リージョンごとに与えられる総量で、そこにあるリソース全部で分け合う形になっています。 1 つが使い切れば、他は自動的に弾かれます。 しかも上限を設定していないリソースは、止める手段がありません。

典型例：Lambda の同時実行数

対処は「予約済み同時実行数」

関数ごとに予約済み同時実行数を設定すると、その分が専用枠として確保され、 同時にその関数の上限にもなります。 重要な関数には確保、暴走しうる関数には制限、という 2 つの意味で効きます。 API Gateway のステージ別スロットリングとまったく同じ考え方です。

主な共有上限

すべてアカウント＋リージョン単位。既定値は変更されている場合があります
サービス共有される枠既定値枯渇したときに起きること
Lambda同時実行数1,000全関数が Throttles で失敗し始める
API Gatewayスロットリング10,000 rps / バースト 5,000全 API が 429 を返す
API GatewayAPI の数600新規 API が作れない
API GatewayVPC Link の数20プライベート統合が追加できない
IAMロール数 / ポリシー数1,000 / 1,500新規ロールが作れない
EC2vCPU 数（タイプ別）タイプによるインスタンスが起動できない
VPCVPC 数5新規 VPC が作れない
VPCElastic IP の数5NAT Gateway が作れない
S3バケット数10,000新規バケットが作れない
CloudFormationスタック数2,000デプロイが失敗する
SES送信レート / 日次上限サンドボックス状態メールが送れない
CloudWatchダッシュボード数 / アラーム数無料枠あり課金が始まる（作成自体は可能）
引き上げ申請という選択肢

多くはサービスクォータから引き上げ申請ができます。枠が足りないだけなら、 アカウントを分けずに増やすほうが安く済みます。 ただし枠を増やしても「共有である」ことは変わりません。 個別の上限設定は結局必要になるので、 まず個別上限を入れて実態を測り、それでも足りなければ申請、という順序が健全です。

02

1つしか持てない設定

分けたくても構造上分けられないものです。要件がここに当たると、アカウント分割が唯一の手段になります。

サービス設定影響範囲
請求支払い方法、請求書アカウント単位が最小。タグでは分けられない
IAMパスワードポリシー全 IAM ユーザーに同一
S3パブリックアクセスブロック（アカウントレベル）全バケットに一括適用
EBSデフォルト暗号化、デフォルト KMS キーリージョン単位で 1 つ
API GatewayCloudWatch Logs のロール ARN全 API で共通。1 つだけ別ロールにはできない
Cost Explorerコスト配分タグの有効化管理アカウントでのみ設定
Config記録対象リソースの設定リージョンごとに 1 つ
CloudTrail証跡の設定分けられるが、実務上は 1 本にまとめる
OrganizationsSCP の適用アカウントまたは OU 単位が最小
請求の分離はタグでは代替できない

「部署ごとにコストを把握したい」ならタグで足ります。 しかし「部署ごとに請求書を分けたい」「支払い方法を分けたい」となると、 アカウント分割以外に手段がありません。ここは要件の言葉づかいを詰めておく価値があります。

03

名前空間の衝突

同じ名前が使えない、というタイプです。命名規約で回避できるので、分割の理由にはなりません。

サービス一意でなければならないもの範囲
IAMロール名、ユーザー名、ポリシー名アカウント内
S3バケット名全世界
CloudWatchロググループ名、ダッシュボード名アカウント＋リージョン
ECRリポジトリ名アカウント＋リージョン
Secrets Manager / SSMシークレット名、パラメータ名アカウント＋リージョン
CloudFormationスタック名アカウント＋リージョン
API Gatewayカスタムドメイン名全世界（DNS のため）

命名規約の型

環境名とシステム名を接頭辞に置くのが定石です。衝突回避と、一覧での判別を同時に満たせます。

{環境}-{システム}-{リソース種別}-{用途}

dev-commapi-agw-api-hotelsearch
prod-commapi-agw-api-hotelsearch

ロググループも同じ考え方で階層を切ります。 サービスごとの名前空間を分けておくと、権限設計と保持期間の管理が楽になります。 

/aws/apigateway/{システム}/{API}-{ステージ}/access
/aws/lambda/{システム}/{関数名}
04

巻き添えリスク

枠でも設定でもないのに、影響が及んでしまうものです。見落とされがちですが、実務ではこれが一番効いてきます。

事象何が起きるか
コントロールプレーンの API レート制限DescribeInstances などの呼び出し制限はアカウント共有。CI/CD が回りすぎると、他のツールが RequestLimitExceeded で失敗する
GuardDuty / Security Hub の検出結果アカウント単位で混在。開発環境のノイズに本番の検知が埋もれる
AWS サポートケースアカウント単位。開発の問い合わせと本番障害が同じ列に並ぶ
IAM ロールの信頼関係同一アカウント内は到達しやすい。信頼ポリシーの誤設定が横断的な権限漏れになる
誤操作の影響範囲terraform destroy の対象を間違えたとき、同じアカウントなら本番も射程内
アカウント境界は人的ミスに対する最も硬い壁

最後の項目が、アカウント分割の実務上いちばん大きい理由です。 IAM で権限を絞る努力より、そもそも到達できない場所に置くほうが確実です。 本番と開発を分ける最大の価値は、枠の分離よりも「事故が越えられない線を引くこと」にあります。

05

分けなくてよいもの

ここが本題かもしれません。「分けたい」と言われる要件の多くは、 アカウントを分けずに満たせます。

やりたいこと分割が必要か代わりの手段
ログを分けたい不要ロググループを分ける。保持期間も権限もここに紐づく
メトリクスを分けたい不要ディメンションで分かれる。設定も不要
権限を分けたい不要IAM ポリシーのリソース ARN を絞る
コストを把握したい不要タグを付け、コスト配分タグを有効化する
ネットワークを分けたい不要VPC・サブネットを分ける
アラートの宛先を分けたい不要SNS トピックを分ける
デプロイを独立させたい不要スタック・パイプラインを分ける
流量の相互影響を断ちたい必要総枠が共有のため（個別上限で緩和は可能）
請求書を分けたい必要タグでは代替できない
誤操作を物理的に防ぎたい必要IAM では限界がある
分割にもコストがある

アカウントを増やせば、IAM の設計、クロスアカウントのアクセス、 ログの集約、ネットワーク接続（Transit Gateway など）がすべて必要になります。 運用の手間は確実に増えます。 上の表で「不要」に当たる要件しかないなら、 同一アカウント内でタグと命名規約で整理するほうが総コストは低く済みます。

06

分割の判断基準

3 つの問いのどれかに当てはまるなら分割、当てはまらないなら同一アカウントで整理する、という判断になります。

一般的な分割の単位

アカウント役割優先度
本番顧客に提供する環境最優先。ここを守るための分割
ステージング本番同等の検証本番と同じ構成を持つ
開発日常の開発・実験負荷試験もここで
監査ログCloudTrail・Config の集約先改ざん防止。書き込み専用に近い権限
共有サービスCI/CD、ECR、DNS など各環境から参照される

本番 / ステージング / 開発の 3 分割が最小構成で、 そこに監査ログ用・共有サービス用を足していくのが AWS の推奨する形です。 Organizations と Control Tower を使うと、 この払い出しと初期設定（SCP、CloudTrail、ログ集約）を標準化できます。

請求は Organizations の一括請求でまとめられるので、 アカウントを分けても支払いは 1 本にできます。 「分けると請求が煩雑になる」という懸念は、ここで解消できます。

07

分けずに守る手当て

すぐには分割できない、という状況のほうが多いはずです。 その場合でも、共有枠の食い合いは個別上限でかなり緩和できます。

共有枠入れておく手当て
Lambda 同時実行数関数ごとに予約済み同時実行数。重要な関数には確保、暴走しうる関数には制限
API Gateway スロットリングステージごとにレートとバースト。既定の 10,000 は「無制限」と同義
コントロールプレーンの API 呼び出しCI/CD のポーリング間隔を延ばす。describe 系の連打を避ける
Elastic IP / VPC 数使っていないものを定期的に棚卸し
IAM ロール数一時的に作ったロールを消す運用ルール

値の決め方

勘で決める必要はありません。CloudWatch に実績があります。 ConcurrentExecutions や Count を 1 分の最大値で見て、 実測ピークに 3〜5 倍の余裕を持たせた値を入れます。 実測 20 rps に対して 10,000 が設定されている、というのはよくある状態です。

上限を入れる順序

いきなり全部に厳しい値を入れると、正常な処理まで弾かれます。 ① 実測値を取る → ② 余裕を持たせた値を入れる → ③ Throttles や 429 を監視する、 という順で進めてください。特に③のアラームを先に用意しておくと、 設定が厳しすぎた場合にすぐ気づけます。

棚卸しの観点

  • ドメインにマッピングされていない未使用ステージ
  • 呼ばれていない Lambda 関数（Invocations がゼロ）
  • アタッチされていない Elastic IP（課金対象）
  • 保持期間が無期限のロググループ
  • 詳細メトリクスが有効なまま放置されている API

いずれも枠と料金の両方に効きます。 分割の是非を判断する前に、まずこの棚卸しをすると、実際の必要量が見えてきます。
