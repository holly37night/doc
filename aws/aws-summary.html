02

通信の通り道と関所

ネットワークは「インターネットからリソースまでの通り道」と「その途中に立っている関所」で考えると整理できます。まず通り道の全体像です。

どこで何が絞られるか

制御するもの何を制御するか単位イメージ
Route 53どの IP へ向かうかドメイン名案内板
WAFリクエストの中身、国、レートCloudFront / ALB手荷物検査
Shield大量の攻撃トラフィックエッジ全体群衆の整理
Internet GatewayVPC とインターネットの接続そのものVPC正面玄関
ルートテーブルどこへ行けるかという経路サブネット館内の通路
ネットワーク ACLサブネットへの出入り（拒否も書ける）サブネットフロアの警備
セキュリティグループリソースへの出入り（許可のみ）ENI部屋のドアの鍵
NAT Gateway内→外は通す、外→内は通さないサブネット一方通行の通用口
VPC エンドポイントインターネットを通らない接続VPC建物内の直通路

同じ「止める」でも手段が違う

  • 来させない — Route 53（そもそも IP を教えない）
  • 中身で弾く — WAF（不正なリクエストパターン）
  • 道を作らない — ルートテーブル（プライベートサブネット化）
  • ドアを閉める — セキュリティグループ（ポートとソース IP）
  • フロアごと遮断 — ネットワーク ACL（特定 IP の拒否）
  • 出るだけ許す — NAT Gateway
  • 公道を通らない — VPC エンドポイント / Direct Connect
03

ビル1棟のたとえ

AWS という貸しビル街に自社専用のビルを 1 棟借りる。中をフロアに区切り、館内の通路を設計し、 正面玄関と通用口を付け、各部屋のドアに入室ルールを決める。 この構図がそのまま VPC の設計に対応します。

最大の誤解ポイント

サブネットに「パブリック」「プライベート」という設定項目は存在しません。 違いはルートテーブルに 0.0.0.0/0 → igw-xxx が書かれているかどうか、それだけです。 隠しているのではなく道が無い状態であり、これが AWS で最も強力な防御になります。

6 つの用語

VPC — 自社専用のビル1棟

AWS の中に確保した閉じたネットワーク空間。作成時に住所の範囲を決めます。 10.0.0.0/16 なら約 6.5 万個の IP を使う宣言です。 CIDR は後から縮められないので、迷ったら /16。 社内ネットワークと将来つなぐ予定があるなら、IP 範囲が重複しないようにします。

サブネット — ビル内のフロア

VPC の住所範囲を用途ごとに切り分けた区画。必ず 1 つのアベイラビリティゾーンに閉じるため、 同じ用途のサブネットを 1a と 1c の 2 つ作るのが基本形です。 /24 は 256 個に見えますが、AWS が 5 個予約するので実際に使えるのは 251 個です。

典型的な切り方
サブネットCIDR用途
public-1a / 1c10.0.1.0/24 · 10.0.2.0/24ALB、NAT Gateway
private-1a / 1c10.0.11.0/24 · 10.0.12.0/24EC2、アプリケーション
db-1a / 1c10.0.21.0/24 · 10.0.22.0/24RDS

ルートテーブル — 館内の通路図

「この宛先へ行くには、この出口を通れ」という道案内のリスト。ここに書かれていない場所へは、物理的に行く手段がありません。

パブリックサブネット用
送信先ターゲット意味
10.0.0.0/16local自分の VPC 内。自動で作られ削除できない
0.0.0.0/0igw-0a1b2c3d上記以外すべて。Internet Gateway へ流す

プライベートサブネット用は 2 行目が nat-xxxxx になります。ルートはより具体的な指定が優先されるため、範囲の狭い 10.0.0.0/16 が先に効きます。

Internet Gateway — ビルの正面玄関

VPC とインターネットをつなぐ唯一の出入り口。作業は「作成して VPC にアタッチ」「ルートテーブルに経路を書く」の 2 手順だけです。 アタッチしただけでは何も起きません。正門を設置しても、案内図に載らなければ誰もたどり着けないからです。 加えてパブリック IP（または Elastic IP）も必要になります。IGW 自体は無料で、冗長化と帯域は AWS 側が面倒を見ます。

NAT Gateway — 社員専用の通用口

プライベートサブネットの EC2 でも yum update や外部 API 呼び出しで外に出たい。 でも公開はしたくない。この矛盾を解決します。

配置とコスト

NAT Gateway はパブリックサブネットに置きます。NAT 自身が外に出られなければ意味がないからです。 また常時課金（東京でおよそ月 5,000 円前後）＋データ処理料がかかり、AZ ごとに置けば台数分になります。 検証環境では止める、S3 アクセスは VPC エンドポイントに逃がす、といった工夫が効きます。

セキュリティグループ — 部屋のドアの入室ルール

リソース 1 台ごとに付く「誰からのどの通信を受け入れるか」のルールです。

Web サーバー用のインバウンドルール
タイプポートソース意味
HTTP800.0.0.0/0誰でも閲覧できる
HTTPS4430.0.0.0/0誰でも閲覧できる
SSH22203.0.113.10/32この IP からのみ管理接続

最大の武器は、ソースに IP ではなく別のセキュリティグループを指定できることです。 DB 側に「ソース = sg-web」と書けば、EC2 が増減して IP が変わってもルールを直す必要がありません。

セキュリティグループとネットワーク ACL

セキュリティグループネットワーク ACL
適用先インスタンス（ENI）サブネット
ルール許可のみ許可と拒否の両方
状態管理ステートフルステートレス
デフォルト受信すべて拒否 / 送信すべて許可すべて許可

ステートフルとは「行きを許可すれば帰りは自動的に通る」という意味です。 セキュリティグループで 80 番の受信を許可すれば、応答は何も設定しなくても返ります。 一方ネットワーク ACL はステートレスなので、戻り用にエフェメラルポート（1024–65535）宛の送信ルールも書かないと通信が成立しません。

実務では普段はセキュリティグループだけで設計し、ネットワーク ACL はデフォルトのままにするのが一般的です。 触るのは「特定 IP を完全にブロックしたい」など、拒否ルールが必要な場面に限られます。

つながらないときのチェック順

Web サイトを公開するには次の 3 つがすべて必要です。裏を返せば、これがそのまま切り分けの順番になります。

  1. 経路

    ルートテーブルに 0.0.0.0/0 → IGW があるか。つまりパブリックサブネットにいるか。

  2. 住所

    パブリック IP または Elastic IP を持っているか。

  3. 許可

    セキュリティグループで該当ポートの受信を許可しているか。

ここまでで見つからなければ、ネットワーク ACL → OS 側のファイアウォール → アプリのリッスン設定、の順に降りていきます。

構築の順番

VPC を作る
 → サブネットを切る（AZ ごとに 2 つずつ）
 → IGW を作ってアタッチ
 → ルートテーブルを作り、サブネットに紐づける
 → NAT Gateway をパブリックサブネットに置く
 → セキュリティグループを作り、リソースに付ける
04

API Gateway でできること

バックエンド（Lambda、EC2、ECS、他社 API など）の手前に立って、共通処理を肩代わりするサービスです。認証やログをアプリ側で実装しなくてよくなるのが最大の価値になります。

できること内容
ルーティングパスやメソッドごとに別々のバックエンドへ振り分ける
認証・認可IAM、Cognito、JWT、Lambda オーソライザーで門前払い
流量制御スロットリング（rps）とクォータ（月間上限）
リクエスト検証必須パラメータや JSON スキーマを検査し、不正なら 400 を即返す
変換リクエスト・レスポンスの形を書き換える
キャッシュ同じリクエストへの応答を保持し、バックエンドを叩かない
CORS 対応プリフライト応答を自動生成
監視アクセスログ、実行ログ、メトリクス、X-Ray
公開制御独自ドメイン、社内限定公開、WAF 連携

入り口の分け方

入り口は 3 つの意味で分けられます。

公開範囲そのものを分ける（エンドポイントタイプ）

タイプ到達経路用途
Regionalインターネットから直接一般的な公開 API

ドメインで分ける

order-api.example.com と member-api.example.com のように、API ごとに別のカスタムドメインを割り当てます。

1 つのドメインの下でパスで分ける

実務で最もよく使われる形です。次の図がこれにあたります。

グループごとに分けて管理する

api.example.com/orders/*  →  注文API（○グループ）の prod ステージ
api.example.com/users/*   →  会員API（×グループ）の prod ステージ

別 API に分けると何が分離されるか

分離されるもの内容
アクセスログステージごとに出力先のロググループを指定できる
実行ログAPI-Gateway-Execution-Logs_{api-id}/{stage} に自動で分かれる
メトリクスCloudWatch の ApiName ディメンションで分かれる
スロットリングステージ単位。片方が詰まっても波及しない

コスト配分API 単位でタグを付けられる

上の一覧は「API とステージを分けたこと」によって生じています。 カスタムドメインは入り口の看板にすぎません。2 つのドメインを同じ API・同じステージに向ければ、 ログもスロットリングも権限も全部ひとまとめのままです。

3 パターンでの整理
構成上の一覧は実現できるか
1 ドメイン ＋ 2 API（ベースパス分け）できる
2 ドメイン ＋ 2 APIできる（ドメイン固有の設定も分けられる）
2 ドメイン ＋ 1 APIできない（ドメイン以外は全部共通）

ドメインを分けて追加で得られるのは、TLS と DNS まわりだけです。

  • 証明書の分離（片方だけワイルドカード、など）
  • 相互 TLS（mTLS）の個別設定
  • 最小 TLS バージョンの個別設定
  • Route 53 のフェイルオーバーや加重ルーティングをグループ単位で
  • 対外 API と社内 API で名前空間ごと分ける

ベースパスマッピングの設定手順

先に確認する 3 つ

① ドメインを所有していること（Route 53 のホストゾーンがあると楽）
② ACM の証明書。リージョンエンドポイントなら API と同じリージョン、エッジ最適化なら必ず us-east-1
③ 各 API がステージにデプロイ済みであること。未デプロイの API は選択肢に出てきません

  1. ACM で証明書を発行する

    エンドポイントタイプに応じたリージョンで「証明書をリクエスト」→「パブリック証明書」。ドメイン名に api.example.com または *.example.com を入力し、DNS 検証を選びます。Route 53 なら「Route 53 でレコードを作成」ボタンで完了。「発行済み」になるまで数分待ちます。

  2. カスタムドメイン名を作成する

    API Gateway コンソール →「カスタムドメイン名」→「作成」。ドメイン名、エンドポイントタイプ、最小 TLS バージョン（1.2）、ACM 証明書を選択します。証明書がプルダウンに出ない場合はリージョン違いを疑ってください。

  3. API マッピングを追加する

    作成したドメインの「API マッピング」タブ →「API マッピングを設定」。API に「注文API」、ステージに「prod」、パスに orders（先頭スラッシュ不要）。続けてもう 1 行追加し「会員API / prod / users」を登録して保存します。REST API と HTTP API の混在も可能です。

  4. DNS レコードを向ける

    詳細画面の「API Gateway ドメイン名」（d-xxxxx.execute-api...）をコピー。Route 53 で「レコードを作成」→ 名前 api、タイプ A、エイリアスをオン →「API Gateway API へのエイリアス」。外部 DNS なら CNAME で指します。

  5. 動作を確認する

    https://api.example.com/orders/... にアクセスします。ベースパスはバックエンドへ渡す際に取り除かれます。/orders/list は注文 API 側のリソース /list に届くので、API 側に /orders を作る必要はありません。

  6. 既定のエンドポイントを無効化する

    疎通確認が取れたら、各 API の「API 設定」で「デフォルトのエンドポイント」を無効化し、カスタムドメイン経由に限定します。

つまずきやすい点

反映時間：リージョンエンドポイントは数分、エッジ最適化は CloudFront の作成を伴うため最大 40 分ほどかかります。
リダイレクト：バックエンドが Location: /list のような相対パスを返すと、ベースパスが抜けた状態でクライアントに届きます。完全な URL を組み立てるか、ステージ変数でベースパスを渡します。
スロットリングの総枠：上限はリージョンあたりアカウント単位（既定で 10,000 rps）で共有されます。API を分けただけでは総枠を奪い合うため、各ステージに明示的な上限を設定してください。

現状と次の一手

現状は「カスタムドメイン 2 つ、API 2 つ」で 1 対 1 に対応している構成です。

API を分けたこと自体は、分離を可能にしただけで有効化はしていません。既定のままだと次の状態になっている可能性があります。

項目既定の状態実質どうなるか
アクセスログ無効どちらのログも存在せず、障害時に追えない
実行ログOFF同上
スロットリング未設定アカウント全体の枠を 2 つで奪い合う。片方の暴走で両方落ちる
WAF未関連付けどちらも保護なし
コスト配分タグ未設定Cost Explorer で内訳が見えない
IAM 権限広いポリシーのままチーム A が誤ってチーム B の API をデプロイできる

設定場所の一覧

分離したいものコンソールでの場所設定内容
アクセスログステージ →「ログとトレース」→ 編集カスタムアクセスログを有効化し、専用ロググループの ARN を指定
実行ログ同上ログレベルを ERROR または INFO に。出力先は API ID ごとに自動で分かれる
詳細メトリクス同上メソッド単位で見たい場合に有効化（追加課金あり）
X-Ray同上トレースを有効化
スロットリングステージ → ステージの詳細 → 編集レートとバースト。メソッド単位の上書きも可能
WAFステージ →「ウェブ ACL」グループ用の Web ACL を関連付け
リソースポリシーAPI →「リソースポリシー」IP 制限や VPC エンドポイント限定が必要な場合
コスト配分タグAPI →「タグ」タブGroup=orders のようなタグ
IAM 権限IAM コンソールリソースを arn:aws:apigateway:{region}::/restapis/{API ID}/* で限定
先に 1 回だけ必要な設定

実行ログを出すには、アカウント単位で CloudWatch Logs へのロール ARN を登録しておく必要があります。 API Gateway コンソールの「設定」→「CloudWatch ログのロール ARN」です。ここが空だとログ設定を保存できません。

優先順位

  1. アクセスログ

    これが無いと何も分析できません。グループ専用のロググループを指定します。

  2. スロットリング

    一方の障害が他方へ波及するのを防ぎます。入れないと API を分けた意味が半減します。

  3. コスト配分タグ

    数秒で終わるわりに、後から「どちらがコストを食っているか」が見えるようになります。

  4. IAM 権限の絞り込み

    チームが分かれているなら優先度が上がります。

  5. WAF

    外部公開していて攻撃リスクがあるなら。REST API のみ対応です。

今すぐ確認できること

  • 各 API のステージ →「ログとトレース」で、カスタムアクセスログが有効かつロググループが別々になっているか
  • 各 API のステージ詳細で、スロットリングのレートが空欄になっていないか
  • CloudWatch のロググループに API-Gateway-Execution-Logs_{api-id}/prod が 2 つ分あるか
もし API を分割する必要が出たら

ドメインが既に分かれている場合、URL を変えずに内部だけ分割できます。 既存 API のステージから OpenAPI 3 を「API Gateway 拡張機能を含めて」エクスポートし、 paths をグループごとに分けて新 API としてインポート。Lambda のリソースベースポリシー、 使用量プランの紐付け、リソースポリシーを手動で補ってからデプロイし、 最後にドメインの API マッピングを張り替えます。旧 API を残しておけば、 切り戻しはマッピングを戻すだけで数十秒で済みます。
